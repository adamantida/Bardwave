# План развития Bardwave (на базе egui)

Статус: черновик плана, код не менялся. Составлен по состоянию репозитория на v1.4.0.

## 0. Принципы и решения

**GUI остаётся на egui.** Переписывать 7 тыс. строк ради вида нет смысла; ценность — в функциях (сцены, кроссфейд, хоткеи), а не в виджетах.

**Сквозные правила для всех этапов:**
1. **Обратная совместимость `config.toml`.** Все новые поля — `#[serde(default)]`, старые конфиги грузятся без ошибок. Тест на загрузку конфига v1.4.0 обязателен в каждом этапе, который трогает схему.
2. **Аудиопоток не блокируется.** Микшер работает в аудио-колбэке под `RwLock`; всё новое (фейды, планировщик случайных звуков) считается в нём без аллокаций и без I/O. Тяжёлое (декодирование, диск) — вне колбэка.
3. **GUI не блокируется.** Прежний стиль: типизированные команды (`AudioCommand`, `ServerCommand`, `ControlAction`), никакой работы на render-потоке.
4. **Один источник правды для управления.** Сейчас GUI шлёт `AudioCommand`, а headless-режим и `/control` ходят через отдельный `ControlAction`/`Board`. Новые функции (сцены, хоткеи, пульт) должны попадать в обе ветки, поэтому в этапе 1 общую логику выносим в одно ядро (см. 2.1).
5. **Тесты.** Каждый этап добавляет юнит-тесты и, где есть сеть, сквозной тест в `tests/`. `cargo fmt --check`, `cargo clippy --all-targets --locked`, `cargo test --all-targets --locked` должны проходить на Windows, Linux и (после этапа 0) macOS.
6. **Версионирование.** Каждый этап — отдельный минорный релиз (1.5.0, 1.6.0, …), релиз собирается существующим `release.yml`.

**Что нужно учесть из текущей архитектуры:**
- Звуки в библиотеке идентифицируются **по пути файла** (`Library::sound(&Path)`), а не по ID. Для сцен нужен стабильный ID звука (см. 2.1), иначе переименование или перемещение файла ломает ссылки.
- Все звуки декодируются **целиком в память** (`DecodedAudio`). Для длинной музыки (этап 5) это около 1.4 ГБ на час стерео f32 при 48 кГц; нужен стриминговый декодер.
- Fade в микшере сейчас жёстко 10 мс (`RAMP_FRAMES = 480`) и служит только для защиты от щелчков. Кроссфейд требует настраиваемой длительности.
- Страница `/control` открывается только с локальной машины, и это сознательное решение; пульт с телефона требует отдельной модели доступа (этап 6).

## Этап 1. Сцены и пресеты (v1.5.0) — размер L

**Цель:** одним нажатием включить набор звуков с нужными громкостями. Это главная недостающая функция для проведения игры.

### 1.1 Модель данных

Добавить в `src/config.rs`:

```toml
[[library.sounds]]
id = "uuid"            # НОВОЕ: стабильный ID (генерируется при загрузке старого конфига)
path = "…"
# остальные поля как раньше

[[library.scenes]]
id = "uuid"
name = "Таверна"
color = "#a04a4a"      # опционально, для цвета кнопки
fade_in_ms = 2000
fade_out_ms = 2000
stop_others = true     # гасить звуки, которых нет в сцене

[[library.scenes.items]]
sound = "uuid-звука"
volume = 0.4
looped = true
start = "on_enter"     # on_enter | manual
delay_ms = 0           # смещение старта внутри сцены
```

- `Library` (`src/gui/groups.rs`) получает `scenes: Vec<Scene>` и методы `add_scene / rename_scene / remove_scene / set_item / remove_item / reorder`.
- Миграция: при загрузке конфига без `id` у звуков генерируем UUID и сохраняем при следующей записи. Ключ в `Library` остаётся путь, добавляется индекс `id → path`.
- Удалённый из библиотеки звук автоматически убирается из сцен (или помечается «файл отсутствует», не ломая сцену).

### 1.2 Ядро управления (общее для GUI, headless и `/control`)

Новый модуль `src/audio/director.rs`:
- `Director` хранит активную сцену, снимок текущего состояния (какие звуки играют, с какой громкостью) и принимает `DirectorCommand::{ActivateScene(id), StopScene, SnapshotToScene(id), ...}`.
- `ActivateScene` вычисляет diff «что играет сейчас → что должно играть» и выдаёт набор операций для движка: старт, смена громкости, остановка. Кроссфейд (этап 2) подключается к этой же точке.
- `Board` в `control.rs` и GUI оба обращаются к `Director`, а не напрямую к движку. Это убирает дублирование логики между консолью и headless.

### 1.3 GUI

- Новая вкладка/панель **Scenes** рядом с группами: сетка кнопок-сцен, активная подсвечена.
- **«Сохранить текущий микс как сцену»**: снимок играющих звуков с их громкостями, лучший способ создавать сцены, не настраивая их вручную.
- Диалог редактирования сцены: список звуков, ползунки громкости, loop, fade-in/out, «останавливать остальные».
- Контекстное меню звука: «Добавить в сцену…».
- Правка существующих диалогов (`src/gui/dialog.rs`, перечисление `Dialog` в `app.rs`): `NewScene`, `RenameScene`, `DeleteScene`, `EditScene`.

### 1.4 Управление и сеть

- `ControlAction::ActivateScene(usize)`, `StopScene`; в `BoardState` — список сцен и активная.
- Эндпоинты `/api/control/scene/activate`, `/api/control/scenes`; кнопки сцен на странице `/control`.

### 1.5 Тесты

- Юнит: миграция старого конфига (id генерируются, сцен нет); diff активации сцены (запуск/остановка/смена громкости); удаление звука чистит сцены.
- Интеграционный: `tests/scenes_model.rs` по образцу `groups_model.rs`; активация сцены через `Board` в headless.

**Критерии готовности:** сцена из 5 звуков включается одним кликом; «сохранить микс как сцену» воспроизводит тот же звук; конфиг v1.4.0 открывается без потерь.

## Этап 2. Кроссфейд и фейды (v1.5.0 или v1.5.1) — размер M

**Цель:** плавные переходы между сценами. Пункт из roadmap.

**Задачи:**
1. **Параметризовать фейд в микшере** (`src/audio/mixer.rs`): вместо константы `RAMP_FRAMES` у трека появляется `ramp_frames` (текущее поведение 480 по умолчанию для щелчков). Новые методы `fade_track_to(id, target_gain, duration)`, `play_track_with_fade_in(id, duration)`, `stop_track_with_fade_out(id, duration)`.
2. **Кривая фейда:** линейная даёт провал громкости посередине при кроссфейде. Использовать equal-power (sin/cos) для пар «уходящий/входящий». Выбор кривой — в конфиге сцены (`curve = "equal_power" | "linear"`).
3. **`PendingHalt` с длительностью:** сейчас `halt` выставляет цель 0 за 10 мс; расширить, чтобы длинный fade-out доходил до тишины и только потом ставил на паузу/стоп.
4. **Прерывание фейда:** повторная активация сцены в середине фейда должна продолжать от текущего `gain`, а не прыгать (не терять значение).
5. **Лимитер:** проверить, что при кроссфейде суммарная громкость не заставляет лимитер «качать» (`LIMIT_RELEASE_SECS`); при необходимости учесть при вычислении gain.
6. **GUI:** общий ползунок «Время перехода» (по умолчанию из сцены), кнопка «Остановить с затуханием» и «Stop all» с фейдом.
7. **Тесты:** юнит-тесты микшера на форму кривой (энергия суммы постоянна при equal-power ±0.5 дБ), на прерванный фейд, на то, что трек останавливается ровно после фейда; тест, что короткий щелчко-защитный ramp не изменился.

**Критерии готовности:** переход между двумя сценами по 3 секунды без провала громкости и щелчков; смена сцены посреди перехода не даёт скачка.

## Этап 3. Горячие клавиши и пульт (v1.6.0) — размер M

**Цель:** запускать стингеры и сцены мгновенно, не мышью.

6. **Стингеры:** режим «one-shot поверх всего» — не гасит остальные звуки сцены и не зависит от активной сцены.
7. **Тесты:** парсер строки сочетания клавиш (платформенные модификаторы Cmd/Ctrl), поиск конфликтов, диспетчеризация действия в `Director`.

**Критерии готовности:** клавиша запускает звук за <50 мс при свёрнутом окне (глобальный режим); конфликты показываются в диалоге.

## Этап 4. Случайные и периодические звуки (v1.7.0) — размер M

**Цель:** живой эмбиент: «вороны раз в 20–60 секунд», «капли в пещере», «вдалеке гром».

**Модель:** внутри сцены появляется элемент типа **emitter**:
```toml
[[library.scenes.emitters]]
sounds = ["uuid-1", "uuid-2"]   # случайный выбор из набора
min_interval_ms = 20000
max_interval_ms = 60000
volume = 0.5
volume_jitter = 0.15            # разброс громкости
pan_jitter = 0.4                # разброс панорамы (если будет стерео-панорама)
max_overlap = 2                 # не больше N одновременно
```

**Задачи:**
1. **Планировщик** `src/audio/emitter.rs`: отдельный поток-таймер (не аудио-колбэк) с детерминированным ГСЧ (seed можно задать в тестах). Он шлёт `PlaySound` через `Director`.
2. **Привязка к сцене:** при активации сцены emitters стартуют, при смене или остановке — гасятся вместе со сценой; при кроссфейде новые стартуют с фейдом.
3. **Панорама для моно-источников:** добавить pan в трек микшера (сейчас микшер суммирует стерео без панорамы); это самостоятельная подзадача, M.
4. **GUI:** редактор emitters в диалоге сцены; индикатор «следующий звук через …».
5. **Тесты:** распределение интервалов в заданных границах, соблюдение `max_overlap`, остановка при смене сцены, воспроизводимость с фиксированным seed.

**Критерии готовности:** сцена «Лес» с тремя emitters звучит не повторяясь; смена сцены гасит их без хвостов.

## Этап 5. Музыка: плейлисты и стриминг файлов (v1.8.0) — размер L

**Цель:** фоновая музыка с очередью, а не только петли.

**Главный риск:** полное декодирование в память. Час стерео f32 при 48 кГц ≈ 1.4 ГБ.

**Задачи:**
1. **Стриминговый декодер** (`src/audio/decoder.rs` + новый `stream_source.rs`): декодирование порциями в отдельном потоке и кольцевой буфер для микшера. Короткие SFX остаются в памяти (быстрый старт), длинные файлы (порог по длительности, например >60 с) идут через стрим.
2. **Плейлист:** модель `Playlist { items, shuffle, repeat: off|all|one, crossfade_ms }`. Переход к следующему треку — с кроссфейдом из этапа 2.
3. **Сцена + плейлист:** сцена может ссылаться на плейлист как на «музыкальный слой».
4. **Перемотка и позиция:** прогресс и перемотка в GUI; события «трек закончился» из движка в `Director`.
5. **Метаданные:** название/исполнитель из тегов (Symphonia их отдаёт) для отображения.
6. **Нормализация громкости (может пойти сюда или в этап 8):** см. ниже.
7. **Тесты:** стрим даёт те же сэмплы, что полное декодирование (сравнение на тестовых файлах); смена трека без разрыва; `shuffle` не повторяет трек, пока не сыграны остальные.

**Критерии готовности:** трёхчасовой плейлист играет при потреблении памяти <200 МБ без дропаутов, переходы без щелчков.

## Этап 6. Удалённый пульт мастера (v1.9.0) — размер L

**Цель:** управлять сессией с телефона, не вставая из-за стола.

**Проблема:** сейчас `/control` закрыт для всех, кроме 127.0.0.1, чтобы игроки не получили кнопки мастера. Открывать его нельзя без отдельной аутентификации.

**Задачи:**
1. **Отдельный токен мастера** `[server] gm_token` (генерируется, как `access_token`), плюс отдельная ссылка «Пульт мастера» с QR-кодом в панели SERVER. Игровой токен не даёт доступа к управлению.
2. **Защита:** сравнение токена за константное время, ограничение попыток (rate limit по IP), `gm_token = ""` не должен открывать пульт (в отличие от `access_token`, пустое значение здесь = пульт доступен только локально).
3. **Состояние в реальном времени:** WebSocket `/ws/control` вместо опроса `/api/control/state`; сервер рассылает diff состояния (что играет, громкости, активная сцена), чтобы несколько устройств видели одно и то же.
4. **Мобильный интерфейс** `control.html` (адаптивный, крупные кнопки): сцены, стингеры, общая громкость, Stop all, ползунки звуков; без перезагрузки страницы.
5. **HTTPS (опционально, для внешнего доступа):** самоподписанный сертификат или инструкция по туннелю; в LAN достаточно HTTP, но через интернет токен мастера не должен ходить открытым текстом. Решение зафиксировать в README.
6. **Тесты:** игровой токен не открывает `/api/control/*`; мастер-токен открывает; без токена удалённо 401/403, локально по-прежнему работает; два клиента получают согласованное состояние.

**Критерии готовности:** с телефона из LAN можно запустить сцену и стингер; игрок с игровой ссылкой управлять не может.

## Этап 8. Ducking и нормализация громкости (v1.11.0) — размер M

**Задачи:**
1. **Ducking:** кнопка (и хоткей) «Приглушить фон» снижает громкость выбранных слоёв до уровня X за T мс и возвращает обратно. Реализация через общий множитель «bus gain» у группы треков с плавным фейдом из этапа 2. Режим «удерживать»: пока нажата клавиша.
2. **Шины (buses):** разделить треки на `music / ambience / sfx`; у каждой своя громкость и ducking. Расширение микшера: gain на шине перед мастер-лимитером.
3. **Нормализация:** при добавлении звука измерять интегральную громкость (EBU R128, крейт `ebur128`) в фоне и сохранять `gain_db` в конфиге; применять при воспроизведении. Включается настройкой, по умолчанию выключена, чтобы не менять звучание существующих библиотек.
4. **Тесты:** ducking возвращает ровно исходную громкость; нормализация приводит два файла с разной громкостью к одному LUFS ±1; шины не нарушают потолок лимитера.

## Этап 9. Страница слушателя (v1.12.0) — размер M

**Задачи (`src/network/static/app.js`, 2203 строки, `index.html`, `style.css`):**
1. **Автопереподключение** с экспоненциальной задержкой и индикатором состояния; сохранять личную громкость игрока в `localStorage`.

## Порядок и зависимости

```
Этап 0 ─▶ Этап 1 ─▶ Этап 2 ─▶ Этап 3
              │         │
              │         ├──────▶ Этап 4
              │         └──────▶ Этап 5 ──▶ Этап 8
              └──▶ Этап 6 (нужны сцены) ──▶ Этап 9
Этап 7 — независимо, можно параллельно с 3–5
Этап 10 — по мере готовности, macOS-часть можно сделать сразу после этапа 0
```

**Минимальный полезный набор:** этапы 0 → 1 → 2 → 3. После них программа превращается из «списка звуков» в инструмент для проведения сессий.

## Оценка и риски

| Этап | Размер | Главный риск |
|---|---|---|
| 0 | S | Права на запись внутри `.app` на macOS; решается каталогом данных |
| 1 | L | Миграция ID звуков; дублирование логики GUI/headless (решает `Director`) |
| 2 | M | Провал громкости и работа лимитера при кроссфейде |
| 3 | M | Разрешения macOS для глобальных хоткеев |
| 4 | M | Нужна панорама в микшере, которой сейчас нет |
| 5 | L | Стриминговое декодирование без дропаутов в аудио-колбэке |
| 6 | L | Безопасность при выходе в интернет (токен мастера, HTTPS) |
| 7 | M | Корректный перенос путей при импорте |
| 8 | M | Согласование шин с существующим лимитером |
| 9 | M | Поведение iOS Safari (автовоспроизведение, Wake Lock) |
| 10 | M–L | Подпись и нотаризация macOS требуют платного Apple Developer аккаунта |

## Открытые вопросы к владельцу проекта

1. **Целевая платформа.** Основной остаётся Windows, или macOS/Linux тоже полноправные? От этого зависит приоритет этапов 0 и 10.
2. **Нужна ли музыка с плейлистами** (этап 5) или проект остаётся про эмбиент и эффекты? Этап 5 самый дорогой по риску.
3. **Выход в интернет.** Остаётся ли UPnP основным способом для удалённых игроков? Если да, этап 6 нужно делать с HTTPS сразу.
4. **Лицензия и распространение.** MIT; для подписи macOS нужен Apple Developer ($99/год): готовы ли вы платить или macOS-сборка будет без подписи (с предупреждением Gatekeeper)?
5. **`calm-mode-server.patch`.** Это заброшенная идея «спокойного режима» страницы игрока или нужно её дорабатывать?
